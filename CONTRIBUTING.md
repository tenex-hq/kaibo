# Contributing to kaibo

Thanks for working on kaibo! This doc covers the **process** rules: how to
commit, how to release. For the **content** rules - what good code looks
like in this repo - see [AGENTS.md](AGENTS.md).

## Commit conventions

Every commit on `main` **must** follow [Conventional
Commits](https://www.conventionalcommits.org/). Non-conforming commits
are silently dropped from release notes by [cliff.toml](cliff.toml).

### Format

```
<type>(<scope>): <subject>

<optional body - wrap at 72 cols, explain *why*>

<optional footers - BREAKING CHANGE:, etc.>
```

- **Subject**: imperative, lowercase, no trailing period, at most 72
  characters.
- **Body**: keep it. git-cliff renders only the subject in release notes,
  but bodies stay in `git log` for later archaeology - that's the right
  split. Don't compress bodies for release notes' sake.

### Types (ordered as they appear in CHANGELOG.md)

| Type       | Use for                                            | In release notes  |
|------------|-----------------------------------------------------|-------------------|
| `feat`     | New user-visible capability or flag                | **Features**      |
| `fix`      | Bug fix that changes runtime behavior              | **Bug Fixes**     |
| `perf`     | Speed/memory improvement, no behavior change        | **Performance**   |
| `refactor` | Internal restructuring, no behavior change          | **Refactor**      |
| `docs`     | README, AGENTS.md, code comments                    | **Documentation** |
| `test`     | Test-only changes (new tests, fixtures, harnesses)  | **Tests**         |
| `build`    | Cargo.toml, dist-workspace.toml, build scripts      | **Build**         |
| `ci`       | `.github/workflows/`, release automation            | **CI**            |
| `chore`    | Tooling, lockfile bumps, anything else              | **Chores**        |
| `revert`   | `git revert` of a prior commit                      | **Reverts**       |

Anything outside this list is dropped from the changelog - keep to it. If
unsure, default to `chore` (visible under "Chores" - better than dropped).

### Scopes (optional but encouraged)

The scope narrows the type to the verb or surface it touches. Use what's
accurate, don't invent decorative ones. Scopes in this repo track kaibo's
verb surface:

- `query` - retrieval, ranking, citation of corpus hits
- `doctrine` - the domain load path (root-MOC section plus `current` pages)
- `domains` - the domain inventory listing
- `contribute` - writing new or amended knowledge back to the corpus
- `sync` - clone/pull plus qmd index refresh
- `status` - health reporting on the local clone and index
- `config` - `Config::resolve`, environment and config-file handling
- `trust` - the corpus trust boundary (content-as-data enforcement)

### Breaking changes

A breaking change to the CLI surface or JSON output shape:

```
feat(query)!: rename `--drafts` to `--include-drafts`

BREAKING CHANGE: `kaibo query --drafts` is now `kaibo query --include-drafts`.
```

Either the `!` after the type/scope **or** a `BREAKING CHANGE:` footer
triggers a `[breaking]` marker in CHANGELOG.md.

### Examples

```
feat(query): add `--include-drafts` to surface draft pages on request
fix(sync): recurse the qmd literal confinement guardrail
docs: trim doc comments to why, traps, and test pointers
```

## Release flow

Releases are tag-driven. Pushing a `vX.Y.Z` tag triggers cargo-dist's
[release workflow](.github/workflows/release.yml), which builds artifacts
for all four targets, creates a GitHub Release using the matching section
of `CHANGELOG.md` as the body, and updates the Homebrew tap formula.

`.github/workflows/release.yml` is generated by `dist generate` (run via
`dist init` the first time, `dist generate` after any `dist-workspace.toml`
change). **Never hand-edit it** - regenerate it instead, the same rule
already in force for `CHANGELOG.md`.

### Cutting a release

Land all work on `main` with conventional-commit messages, then:

```sh
just release X.Y.Z
```

The recipe in [Justfile](Justfile) is the canonical release flow. It:

1. Checks the version has shape `X.Y.Z` (optionally with a prerelease
   suffix).
2. Checks the current branch is `main`.
3. Checks the working tree is clean.
4. Checks tag `vX.Y.Z` does not already exist.
5. Fetches `origin/main` and checks local `main` matches it exactly, so a
   stale local main can't ship a release that silently drops commits
   already on the remote.
6. Bumps the version in `[workspace.package]` in `Cargo.toml` with a
   scoped `awk` that only touches that section's `version` line - not any
   dependency version string elsewhere in the file.
7. Refreshes `Cargo.lock` (`cargo build --quiet`).
8. Regenerates `CHANGELOG.md` via `git cliff --tag vX.Y.Z -o CHANGELOG.md`.
9. Commits as `chore(release): vX.Y.Z`, creates an **annotated** tag
   (`git tag -a vX.Y.Z -m "vX.Y.Z"`), and pushes with `--follow-tags`.

If you need to run the steps by hand (recipe broken, partial release,
etc.), the equivalent commands, in the same order, are:

1. Confirm the version shape and that you are on `main` with a clean tree.
2. `git tag vX.Y.Z` must not already resolve; `git fetch origin main` and
   confirm `git rev-parse HEAD` equals `git rev-parse origin/main`.
3. Bump the `version` under `[workspace.package]` in `Cargo.toml` by hand.
4. Refresh the lockfile: `cargo build`.
5. Regenerate the changelog: `git cliff --tag vX.Y.Z -o CHANGELOG.md`.
6. Commit: `git commit -am "chore(release): vX.Y.Z"`.
7. Tag and push: `git tag -a vX.Y.Z -m "vX.Y.Z" && git push --follow-tags`.
   The annotated `-a` tag is required for `--follow-tags` to ship it -
   a lightweight tag (`git tag vX.Y.Z`) stays local and no release fires.

Do **not** edit `CHANGELOG.md` by hand - it's regenerated from `git log`.
If a release note is wrong, fix the underlying commit message (or add a
follow-up commit) and regenerate.

### Previewing release notes

```sh
just release-preview X.Y.Z
```

Prints what the release body will look like without writing the file or
touching the tree - useful before you commit a misnamed type.

## Operational traps

These are failure modes specific to this release pipeline. Each has bitten
a project before; check for them rather than assuming a green run means a
complete one.

- **`HOMEBREW_TAP_TOKEN` can expire silently.** The Homebrew publish job
  authenticates to a separate, cross-org tap repository
  (`tenex-hq/homebrew-tap`) with a personal access token that needs
  `contents:write` on that repo. If the token expires or is revoked, the
  `publish-homebrew-formula` job fails, but the `host` job that creates
  the GitHub Release still succeeds - the release looks complete from the
  Releases page and `brew install` keeps serving the previous formula
  with no error to the person who cut the release. After every tagged
  release, check the Actions run for the tag and confirm
  `publish-homebrew-formula` shows success, not just `host`. If it
  failed, refresh the token and re-run that job before telling anyone the
  release is out.
- **Never cut a release by hand once the tag-triggered workflow exists.**
  Compiled binaries are not byte-for-byte reproducible. If a first
  release is built and uploaded manually while a `tags: v*` workflow is
  already wired up, the next push of that same tag (or CI re-running
  against it) rebuilds and re-uploads binaries whose checksums no longer
  match whatever formula or shell installer users already fetched, and
  `brew install` (or the shell installer's checksum check) fails
  verification for anyone who installed in between. Let the workflow cut
  every release, including the first one.
- **The repo must stay public.** `brew install` fetches release assets
  unauthenticated; if the repo ever goes private, the tap formula breaks
  for every user until either the repo is public again or the formula is
  reworked to carry credentials.
